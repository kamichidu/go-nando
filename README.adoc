= nando — 納戸

== About the Name

nando is a Japanese word for a household storeroom: a place to keep useful things that are not needed every day. The name reflects nando's role as a dependable home for files that should be preserved and retrieved when needed.

== Overview

nando is a content-addressed file repository for keeping durable collections of files. It stores file content as immutable objects and organizes names and directories in a separate metadata namespace. A daemon owns a repository while command-line and filesystem clients access it.

The design suits collections that are written, preserved, and read over time. It is less suited to workloads that frequently rewrite files in place, require every write to wait for remote durability, or need replication across multiple remote providers.

== Use Cases

Examples include:

* Photo and video original archives.
* AI model weights, checkpoints, configuration, and evaluation artifacts.
* Project archives, research outputs, and other durable file collections.
* A local-first repository with asynchronous delivery to remote object storage.

For remote delivery, nando currently supports Google Cloud Storage (GCS). Content is committed locally first; delivery to GCS is asynchronous. A repository uses local storage alone or local storage with one remote backend. GCS is the only implemented remote backend. Combining multiple remote backends in one repository is not supported and is not planned.

== Architecture

nando separates the Repository, Metadata Store, and Object Storage responsibilities. The Repository coordinates operations and consistency. The Metadata Store owns file and directory names, hierarchy, and revisions. Object Storage holds immutable file content; its interface is abstract, with local storage and GCS implementations.

The Metadata Store is also an abstract interface. SQLite is the current backend. Other databases, including Firestore, could implement the same interface if they provide equivalent transactional and compare-and-set (CAS) semantics; no alternative backend is currently implemented.

== Requirements

Using a prebuilt release requires a supported operating system and architecture listed with that release. Building from source requires Go 1.25.1 or later. GCS repositories also require Google Cloud credentials with access to the configured bucket. Local repositories do not require cloud credentials.

== Installation

Install the three independent Go modules with:

[source,bash]
----
go install github.com/kamichidu/go-nando/cmd/nando@latest
go install github.com/kamichidu/go-nando/adapters/fuse/cmd/nando-fuse@latest
go install github.com/kamichidu/go-nando/adapters/webdav/cmd/nando-webdav@latest
----

Ensure the Go binary directory is on `PATH`. `go install` places all three
executables in that same directory, so invoke the optional adapters through
`nando fuse` and `nando webdav`:

[source,bash]
----
nando fuse --help
nando webdav --help
----

`nando` finds `nando-fuse` and `nando-webdav` beside its own resolved
executable. It does not search `PATH` for adapters. To build from a checkout
instead, run `go build ./cmd/nando` from the repository root. For Debian
packages and the systemd user service, see the
link:packaging/README.md[package and service guide].

The Debian package exposes only `nando` in `/usr/bin`; run the optional
adapters as `nando fuse` and `nando webdav`. The resolved executable lives in
`/opt/nando/bin`, and those subcommands resolve `nando-fuse` and `nando-webdav`
from `/opt/nando/libexec`. Source builds can set `NANDO_LIBEXEC_DIR` to an
explicit adapter directory for development and tests.

== Quick Start

Initialize a local repository:

[source,bash]
----
nando --repository "$HOME/nando-data" init
----

In one terminal, start its daemon:

[source,bash]
----
nando --repository "$HOME/nando-data" daemon
----

In another terminal, import a file and browse or export it:

[source,bash]
----
nando --repository "$HOME/nando-data" put ./photo.jpg /photos/photo.jpg
nando --repository "$HOME/nando-data" ls /photos
nando --repository "$HOME/nando-data" get /photos/photo.jpg ./photo-copy.jpg
----

The daemon must remain running while clients use the repository. The examples choose a repository path explicitly so every command addresses the same repository.

== Configuration

Without `--repository`, nando uses the `repository` value in its user TOML configuration, or the default data directory (`${XDG_DATA_HOME:-~/.local/share}/nando`). The default configuration file is `${XDG_CONFIG_HOME:-~/.config}/nando/config.toml`. Command-line options take precedence over configuration values.

The TOML repository path is configured as `[repository].path`, and process-wide verbose logging as `[logging].verbose`. Previous top-level `repository` and `verbose` keys are rejected. The `--repository` and `--verbose` CLI flags remain available.

Optional `[daemon].listen` sets the daemon's listening address and the address
CLI commands use to connect. If omitted, both use the repository-specific local
Unix socket. The old `[daemon].endpoint` and top-level `daemon_endpoint` keys are
rejected.

The common `--daemon-listen` flag overrides `[daemon].listen` for all three
binaries. Pass it before `daemon` when setting a listener on the command line.
FUSE and WebDAV settings use `[fuse].mountpoint` / `--fuse-mountpoint` and
`[webdav].listen` / `--webdav-listen` respectively.

A minimal configuration file is:

[source,toml]
----
[repository]
path = "/home/alex/nando-data"

[logging]
verbose = false
----

To initialize remote delivery with the currently supported GCS backend, select the backend and provide a bucket:

[source,bash]
----
nando --repository "$HOME/nando-data" init --delivery-mode remote --remote-backend gcs --remote-bucket my-nando-bucket
----

Remote delivery requires explicit scheduler policy in the daemon's TOML configuration. Example values are deployment choices:

[source,toml]
----
[remote]
sync_idle_interval = "30s"
sync_periodic_interval = "5m"
max_delivery_delay = "30m"
sync_parallelism = 2
----

Repositories use either `local` delivery or `remote` delivery. Remote mode keeps complete content in Local durable staging/cache and delivers it asynchronously to exactly one selected backend. GCS is the only implemented remote backend. Multiple backends, fanout, failover, and tiering are unsupported and not planned.

Existing repositories with `delivery_mode: "gcs"` and `gcs_bucket` remain readable and are not rewritten when opened. TOML scheduler settings are supported only under `[remote]` with the four keys shown above; legacy top-level scheduler keys are rejected as unknown. CLI flags (`--delivery-mode gcs`, `--gcs-bucket`) remain accepted aliases. New repositories and examples use generic names. Reinitializing an existing repository does not change its selected backend or bucket.

The daemon runs remote delivery processing, Capacity GC, and Orphan/Invalid GC as independent tasks. Remote delivery queue rows retain durable enqueue timestamps so maximum-delay eligibility survives daemon restart. See the link:samples/config.toml[configuration example] and link:packaging/README.md[Debian service guide] for setup details.

== Operations

The main commands are `init`, `daemon`, `put`, `get`, `cat`, `ls`, `stat`, `mv`, `rm`, `gc`, `doctor`, `recovery`, and `admin recover`. Run commands with `--help` for their flags and arguments. `doctor` checks repository health; `recovery list`, `recovery retry`, and `recovery discard` manage preserved write work after an interrupted operation.

For safe backup and restore, stop clients and the daemon and preserve the complete repository as one consistent set. Follow the link:docs/backup-restore.adoc[backup and restore guide]. Package installation and service lifecycle details are in the link:packaging/README.md[package guide].

== Operational Considerations

* nando is intended for durable collections, not high-churn files that are repeatedly modified in place.
* Remote delivery is asynchronous, so a successful local commit does not mean the remote copy is already durable. Keep the local repository available until delivery completes.
* A repository uses local storage alone or local storage with one remote backend. nando does not replicate across multiple remote providers.
* Keep the daemon and its repository on storage with enough capacity for the selected workload. Back up the full repository while it is stopped.
* GCS credentials and user configuration are managed outside the repository data directory.

== Project Status

nando is under active development. Local object storage and asynchronous delivery to the single selected GCS backend are implemented, alongside the daemon, CLI, FUSE, and WebDAV clients. User-directed repository-to-repository synchronization is not implemented. Consult the link:docs/phase-a-completion-review.adoc[Phase A completion review] for current status and known gaps.
