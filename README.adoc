= nando

`docs/design.ir.yaml` is the sole semantic authority and direct design reference for this repository. See `docs/design-ir-migration.md` for the one-time source coverage record.

== Validate the design

Check out the official Design IR validator and provide its path:

[source,bash]
----
git clone https://github.com/kamichidu/design-ir.git ../design-ir
git -C ../design-ir checkout 455ed318b7bc409d3e1da320620ef92d457042b9
DESIGN_IR_REPO=../design-ir tools/validate-design-ir.sh
----

The script verifies the pinned schema digest, then validates structure and semantics with the official v1alpha1 validator. Unresolved representation gaps are reported as warnings; validation errors fail the command.

== Reproducible E2E gates

Run host-native G0-G3 and WebDAV G5 checks with:

[source,bash]
----
e2e/run.sh
----

Docker Compose starts only fake GCS; the daemon, real FUSE mount, WebDAV adapter, scenario runner, and fault-injection proxy stay on the Linux/WSL host. The optional bounded binary/concurrency FUSE stress profile is `e2e/run.sh --stress`. Scenario assertions, host requirements, fake-GCS limitations, and retained evidence are documented in link:docs/e2e-gates.md[docs/e2e-gates.md].

== WebDAV Phase A

WebDAV is a separate Go module and process. Build it with `cd webdav && go build ./cmd/nando-webdav`. It connects to the daemon using public controlrpc and daemon-issued `file://` Resource URIs only. Approved Phase A operation is single-user and local-host only: the daemon uses a per-user Unix socket (private parent mode 0700, socket mode 0600), while WebDAV serves unauthenticated plain HTTP on loopback only. External exposure, multi-user authorization, WebDAV client authentication, and TLS termination are deferred. Supported conditional PUT headers and deliberate protocol gaps are documented in link:docs/webdav-phase-a.adoc[WebDAV Phase A].

== Daemon maintenance scheduling

GCS delivery requires an explicit scheduler policy in the daemon's TOML config; timing and parallelism have no implicit operational defaults. Example values below are illustrative and must be selected for the deployment:

[source,toml]
----
gcs_sync_idle_interval = "30s"
gcs_sync_periodic_interval = "5m"
gcs_max_delivery_delay = "30m"
gcs_sync_parallelism = 2
----

The daemon runs transfer processing, Capacity GC, and Orphan/Invalid GC as independent tasks. GCS queue rows retain their durable enqueue timestamps so maximum-delay eligibility survives daemon restart. Idle is currently measured from the last successful content commit observed by the daemon; the Design IR still records the broader idle definition/default policy as an open decision. The scheduler also runs for Local repositories when these settings are explicitly configured; without an explicit policy, Local repositories keep their existing manual maintenance behavior.

== Debian package and systemd

The nfpm Debian package installs the CLI, FUSE and WebDAV executables, plus separate systemd user and system `nando@.service` templates. The user service is the supported Phase A mode and uses each user's XDG configuration, data, and per-user Unix socket. See link:packaging/README.md[Debian package and service setup] for instance configuration and lifecycle instructions. Installation and upgrade do not enable, start, or restart services; removal preserves repositories, configuration, credentials, and the dedicated system account.

The system service template is experimental and is not a Phase A acceptance gate. It uses a dedicated non-login `nando` account, `/etc/nando/<instance>.toml`, `/var/lib/nando/<instance>`, and `/run/nando-<instance>`. Because the control socket remains mode 0600, system-mode FUSE and WebDAV clients must run under the same `nando` account. The template must not be treated as supported multi-user sharing.

== Backup and restore

Backup and restore are operator-managed. Preserve the entire stopped Repository as one consistent set, including SQLite and any sidecars, CAS objects, Recovery staging/manifests, coordination state, repository settings, and pending GCS delivery obligations. The operator chooses the snapshot or copy mechanism; no particular storage technology is required. See link:docs/backup-restore.adoc[Repository Backup and Restore] for the static point, restore checks, and current Recovery path constraint.
