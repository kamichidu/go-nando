= Storage Model

== Overview

A `nando` repository consists of two logically distinct stores:

* a metadata store containing logical namespace entries;
* an object store containing immutable file contents.

The metadata store is the authority for logical path visibility. The object store is the authority for committed content bytes.

Neither store alone represents a complete repository.

== Logical Paths

Logical paths:

* use `/` as the separator on every platform;
* are absolute within the repository namespace;
* are case-sensitive;
* are normalized before reaching repository operations;
* cannot escape the repository root;
* are independent of host filesystem path conventions.

Characters meaningful to a storage backend, including `%` and `_` in SQLite `LIKE`, must be treated as literal logical path characters unless explicitly prohibited by repository format rules.

== Metadata Entry

The current entry model contains:

* logical path;
* content digest;
* size;
* modification time;
* file mode;
* content type;
* entry state;
* directory marker;
* creation and update timestamps.

=== Entry States

`pending`::
An operation is in progress and its object or metadata transition is protected from garbage collection. A pending entry is not visible through normal `get`, `stat`, or `list` operations.

`ready`::
The logical entry is visible and references a committed, verified object, or represents a valid directory according to the selected directory model.

`deleted`::
The logical entry is not visible. Its previous object may be reclaimed when no protected entry references it.

State transitions must be explicit and atomic within the metadata store.

[source,text]
----
absent/deleted -> pending -> ready
pending        -> deleted/aborted
ready          -> deleted
ready          -> pending -> ready   // replacement
----

Direct creation of an invalid `ready` entry is prohibited by design, even if the current low-level scaffolding API still permits it.

== Content Identity

An object identifier is derived from the exact bytes committed to the object store.

Planned default:: SHA-256.

The repository format must identify the digest algorithm. Object identifiers should be algorithm-qualified either in metadata or in object layout so that future migration does not reinterpret existing identifiers.

Examples:

[source,text]
----
sha256:<hex-digest>
objects/sha256/ab/cd/<remaining-digest>
----

The precise layout remains an implementation detail, but repository format metadata must make the algorithm unambiguous.

== Object Store Invariants

A committed object must satisfy all of the following:

. Its identifier is derived from its complete content.
. Its content is immutable after commit.
. Opening the identifier returns the committed bytes or a not-found error.
. Repeating a commit of identical content is idempotent.
. A failed commit does not expose a partial object as committed.
. Temporary objects are not returned by enumeration of committed identifiers.

An API that accepts both a caller-provided digest and arbitrary bytes must verify the relationship before exposing the object as committed.

=== Local Object Store

The local backend should:

. create a temporary file on the same filesystem as the final object;
. stream source bytes into the temporary file while computing the digest;
. flush and close the temporary file;
. atomically rename it to the digest-derived final path;
. handle a concurrently committed identical object as success after verification;
. never overwrite a committed object with different bytes.

The directory containing temporary files is not part of the committed object namespace.

=== Google Cloud Storage Object Store

The GCS backend must provide equivalent observable semantics despite lacking filesystem rename.

Expected strategy:

. upload to a temporary object name;
. compute or verify the digest from uploaded content;
. publish the final digest object using generation preconditions;
. treat an already existing valid digest object as success;
. delete the temporary upload after successful publication;
. retain enough information for later cleanup after interrupted publication.

The exact mechanism is planned work. Backend-specific optimization must not change repository-level commit semantics.

== Repository Layout

Current local layout:

[source,text]
----
<repository>/
|-- metadata.sqlite
|-- objects/
`-- temp/
----

Planned repository-owned metadata:

[source,text]
----
<repository>/
|-- repository.json          // repository format and backend identity
|-- metadata.sqlite          // when using SQLite metadata
|-- objects/                 // when using local object storage
`-- temp/                    // local transient state
----

The repository configuration must record at least:

* repository format version;
* digest algorithm;
* metadata backend and backend-specific location;
* object store backend and backend-specific location;
* directory model when format-dependent.

Per-user CLI configuration may select a repository and presentation preferences, but must not silently redefine repository identity.

== Directory Model

Status:: Open.

Two models remain viable.

=== Implicit Directories

Directories are inferred from file path prefixes.

Advantages:

* smallest metadata model;
* no parent-entry maintenance;
* naturally fits a file collection.

Costs:

* empty directories cannot be represented;
* directory metadata cannot be preserved;
* move and delete require prefix operations;
* filesystem mounting semantics become less direct.

=== Explicit Directories

Directories are stored as first-class metadata entries.

Advantages:

* empty directories are representable;
* directory mode and timestamps can be preserved;
* behavior maps naturally to WebDAV and filesystem adapters.

Costs:

* parent creation and validation rules are required;
* directory entries need field constraints distinct from files;
* subtree operations must preserve hierarchy invariants.

Decision criterion::
Because future Windows Explorer access and filesystem-style behavior are expected possibilities, explicit directories are currently favored, but the decision is not yet locked.

Until decided, implementation must not rely on a mixture of implicit and explicit semantics.

== Metadata Schema Evolution

Repository schema evolution requires an explicit format version.

For SQLite, either `PRAGMA user_version` or a migration table may be used. Migration must be:

* ordered;
* transactional where SQLite permits;
* idempotent at the version boundary;
* rejected when opened by an older unsupported binary;
* tested against a repository created by each supported prior version.

`CREATE TABLE IF NOT EXISTS` alone is initialization, not a complete migration mechanism.

== Time and Mode Representation

Times are stored in UTC and exposed with defined precision. The repository format must not depend on local timezone.

File mode preservation is best-effort across operating systems. Unsupported mode bits must not make content unreadable, but loss of requested metadata should be surfaced when relevant.

== Deleted Metadata Retention

Status:: Open.

Soft-deleted rows currently preserve historical metadata until replaced or manually compacted.

A retention policy must decide whether deleted entries are:

* retained indefinitely as tombstones;
* compacted after object collection;
* retained for a recovery window;
* promoted into a future version-history model.

Garbage collection of object bytes is independent from deletion or compaction of metadata rows.
