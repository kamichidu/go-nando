= Architecture

== Purpose

`nando` is a file repository that separates logical file paths from immutable file contents.

The system stores:

* logical paths and file properties in a metadata store;
* immutable content-addressable objects in an object store.

The initial implementation is a local CLI using SQLite and the local filesystem. The architecture must allow the object store to be replaced by Google Cloud Storage without changing repository semantics.

== Scope

The initial scope is a single repository opened by a CLI process.

The architecture does not yet promise:

* distributed metadata writes;
* multi-host transactional coordination;
* transparent filesystem mounting;
* remote concurrent writers;
* version history exposed to users.

These capabilities may be added later, but must not weaken the invariants defined by the storage and consistency documents.

== Components

=== CLI

Responsibilities:

* parse arguments and flags;
* normalize user input;
* construct runtime dependencies;
* map domain errors to process exit codes;
* connect streams to application operations.

The CLI must not:

* execute SQL directly;
* derive content identifiers;
* decide object reachability;
* implement recovery policy.

=== Application

Responsibilities:

* expose use cases such as `put`, `get`, `list`, `move`, `remove`, `gc`, and `doctor`;
* coordinate repository operations;
* define operation-level input and output structures;
* apply repository-wide operation policy, including locking and recovery boundaries.

Current status::
The scaffolding application layer mostly delegates to `repository.Repository`.

Planned direction::
Use-case orchestration will move toward the application layer when pending-state handling, locking, and recovery are implemented. The repository layer will retain storage coordination primitives and invariants.

=== Repository

Responsibilities:

* coordinate metadata and object storage;
* enforce ordering between object commit and metadata visibility;
* preserve content-addressable identity;
* expose logical repository operations independently of concrete backends.

The repository owns cross-store invariants. Neither the metadata store nor the object store can independently guarantee repository consistency.

=== Metadata Store

Responsibilities:

* store logical entries and their state;
* enforce path uniqueness;
* perform atomic metadata transitions;
* answer reachability queries for garbage collection;
* provide schema migration and repository format compatibility checks.

The initial backend is SQLite.

=== Object Store

Responsibilities:

* commit immutable objects;
* open committed objects for reading;
* verify object content against its identifier;
* enumerate committed object identifiers;
* delete unreachable objects when instructed by garbage collection.

Backends must not assign logical paths. They operate only on content identities.

The initial backend is the local filesystem. Google Cloud Storage is planned.

=== Supporting Packages

`content`::
Defines digest identity and hashing behavior.

`paths`::
Defines logical path normalization independent of host filesystem path syntax.

`config`::
Loads runtime user configuration. Repository format configuration will be introduced separately.

== Dependency Direction

[source,text]
----
CLI
  -> Application
      -> Repository
          -> Metadata Store
          -> Object Store
          -> Content Identity

CLI -> Paths
CLI -> Runtime Config
----

Concrete storage packages depend on storage interfaces and domain value types. Core repository logic must not depend on CLI packages.

== Construction

The composition root belongs to the executable boundary.

It resolves:

* repository location;
* repository format metadata;
* metadata backend;
* object store backend;
* digest algorithm;
* repository lock implementation.

Current status::
The CLI always constructs SQLite plus the local object store.

Planned direction::
Backend selection will be driven by repository-owned configuration stored inside the repository, not only by per-user CLI configuration.

== Repository Operations

=== Put

Target semantics:

. Read source content into a temporary object while computing its digest.
. Determine the content identifier from the bytes actually written.
. Commit or reuse the immutable object.
. Verify the committed object according to backend guarantees.
. Atomically make metadata visible as `ready`.

A caller-supplied digest must not be trusted as proof of object identity.

=== Get and Cat

The metadata entry is resolved first, then the referenced object is opened.

`get` must write through a temporary destination and atomically replace the final path only after successful completion.

`cat` streams directly to the supplied writer and must reject directory entries.

=== Move and Remove

These are metadata operations. They do not rewrite immutable objects.

Path conflict detection must cover the entire affected subtree, not only the root path.

=== Garbage Collection

Garbage collection deletes committed objects that are not protected by any live or in-progress metadata state.

It must not race with `put` in a way that can delete an object before its metadata becomes visible.

=== Doctor

`doctor` validates at least:

* every live metadata reference resolves to an object;
* every referenced object's content matches its identifier;
* metadata states are internally valid;
* repository format is supported.

Repair behavior is separate from detection. `doctor` must not silently mutate repository state unless explicitly invoked in a repair mode.

== Error Model

Domain errors should be typed or sentinel errors and mapped at the CLI boundary.

Stable categories include:

* invalid arguments;
* entry or object not found;
* path conflict;
* repository corruption;
* unsupported repository format;
* repository busy or locked;
* operation interrupted with recoverable pending state.

String matching must not be the primary mechanism for classifying corruption or verification failures.

== Non-Goals of the Scaffolding

The scaffolding is not intended to pre-create every future package. Placeholder packages should be avoided unless they establish a compile-time contract used by current code.

Architecture is preserved through explicit interfaces, invariants, and tests rather than empty directory structure.
