== Decision

The repository has a substantial, tested single-host Phase A implementation: Local and GCS repository modes, the SQLite Metadata and transfer queue, daemon-owned Resource sessions and Recovery, peer CLI/FUSE/WebDAV processes, and real host FUSE and HTTP checks are present. This review does not find a broad failure of the Repository or CAS core.

Phase A cannot be signed off as complete from this checkout. The PA-01 implementation follow-up adds a daemon-owned configured scheduler, and this PA-02 follow-up records the approved single-user local-host security boundary. Scheduler operational defaults and the meaning of idle remain open, as do the other completion items:

. Design IR `OPEN-GCS-SCHEDULER-DEFAULTS` still leaves timing defaults and whether idle means no repository writes or no dirty handles unresolved. GCS mode therefore requires all four scheduler settings explicitly; current code measures idle from the last successful content commit observed by the daemon. That mechanism is implemented and exercised, but this review does not treat the chosen operational interpretation as an accepted Design IR decision. Local-mode GC scheduling also starts only when these scheduler settings are explicitly configured.
. PA-02 is resolved for Phase A by the approved policy recorded in `DES-PHASE-A-DAEMON` and `DES-ADAPTERS-FILESYSTEM`: private per-user Unix socket, loopback-only unauthenticated HTTP WebDAV, no external exposure or multi-user authorization, and explicit conditional PUT handling. `OPEN-ADAPTER-AUTHORIZATION` now tracks future expansion choices only and is not a Phase A blocker.

The Design IR also still labels `DES-PHASE-A-DAEMON.phase_status` as `planned`. That is a formal status mismatch: implementation evidence cannot by itself change the canonical roadmap state. It should be changed only after the owner accepts the remaining decisions and evidence.

These are blockers to a *formal Phase A complete* decision. The findings below distinguish those blockers from intentionally deferred work, operational limitations, and evidence that is not part of the Phase A contract. The original gap review was documentation-only; PA-01 and PA-02 follow-ups made only the scheduler and approved local security-boundary changes.

=== Resource sessions, Recovery, and durable failure outcomes

`REQ-RESOURCE-SESSIONS` and `REQ-RESOURCE-RECOVERY` are substantially implemented in `internal/daemon/session.go`, `internal/daemon/service.go`, `internal/daemon/server.go`, and Repository CAS methods. The reviewed code persists a Begin recovery manifest before returning a mutable staging URI, records failure reason and original expectation, preserves staging on generic Release/expiry/shutdown, reconciles recovery before retry, retains CAS on conflict, and uses discard tombstones for explicit cancellation and FUSE unlink. The same-process and restart paths are exercised by `internal/daemon/service_test.go`, `internal/daemon/server_test.go`, FUSE unit tests, and E2E G1/G3 recovery scenarios. G3-05 verifies successful retry bytes and competing-writer retention, not just metadata size.

*Status: Implemented for Phase A `file://` resources; unit/race and G3 evidence PASS.* Remote resource schemes are explicitly deferred by `REQ-RESOURCE-SESSIONS` and are not a gap.

Remaining verification limits: no process-kill E2E is run at every individual manifest fsync/rename boundary; those persistence-failure branches have unit/fault-double coverage rather than exhaustive power-loss testing. This is not evidence of a known failed invariant, but should not be overstated as hardware-level durability proof.

=== WebDAV adapter and protocol-suite scope

Phase A's IR says read-write WebDAV and requires a separate peer process using the public daemon/Resource contract. It does not enumerate RFC methods, require WebDAV class 2 locks, define dead-property storage, specify COPY replacement behavior, or require Litmus. Therefore:

* `LOCK`/`UNLOCK`, `PROPPATCH`/dead properties, directory COPY, and overwrite semantics are *not independently mandated Phase A features* by the current IR. Their absence is an explicit partial protocol surface, not by itself a Phase A blocker. `DAV:1` is advertised; the adapter refuses LOCK/UNLOCK/PROPPATCH with 501 and omits the unsupported `DAV:supportedlock` capability from allprop/propname; an explicit request returns a 404 propstat. COPY supports only files to absent destinations; MOVE supports non-replacing namespace moves. Full Litmus `copymove`, `props`, and `locks` compliance cannot be claimed.
* `nando-webdav` is a separate module/process using controlrpc and daemon file resources. PUT commits before 201/204 and uses Begin-time Entry/revision/absence as its CAS snapshot for conditional PUT. GET/HEAD/PROPFIND and tested namespace methods use daemon state. G5 curl covered the tested operations.
* The approved Phase A boundary is loopback-only unauthenticated HTTP and same-user local operation. WebDAV PUT enforces `If-Match`/`If-None-Match` against the Begin-time CAS snapshot and rejects unsupported conditions. External exposure, client auth, TLS termination, multi-user authorization, and TCP operations are deferred; these are not Phase A acceptance requirements.
* Litmus and cadaver are unavailable; their suite/client status is SKIP, not PASS. This is not a Phase A scope blocker because neither tool nor full RFC compliance is a Design IR acceptance item. It leaves broader interoperability unverified.

PA-04 is resolved: x/net/webdav's default PROPFIND property generator publishes an exclusive write `<DAV:supportedlock>` even when this adapter intercepts LOCK/UNLOCK and returns 501. The adapter now omits that unsupported property from allprop/propname and responds to an explicit property request with a 404 propstat, without a `lockentry`. RFC 4918 allows resources not to support locking; §6.7 requires `supportedlock` when a resource does support LOCK, and §9.1 requires a 404 result for an explicitly requested property that does not exist. G5 asserts allprop, propname, explicit request, Depth 0/1, `OPTIONS DAV: 1`, and LOCK/UNLOCK 501.

Other unverified WebDAV behavior includes conditions on methods beyond PUT, concurrent HTTP updates, non-empty collection DELETE behavior, MOVE/COPY precondition handling, persisted content-type presentation, and errors at every Resource cleanup boundary. The approved contract covers PUT's Begin-time ETag conditions; this review does not extend that contract to other methods.
