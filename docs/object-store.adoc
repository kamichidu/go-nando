= Object Store Model

The Object Store is responsible for persisting and validating raw, immutable content-addressable data files.

== Storage Contract

The Object Store guarantees three primary characteristics:

* **Content Addressable Storage (CAS)** ::
Objects are identified and accessed strictly by their content cryptographic hash. The store makes no assumptions about logical file paths.

* **Eventual Consistency** ::
The Object Store is eventually consistent (Eventually Consistentである). The details of this model are:
+
--
* **Immediate Writer Visibility** :: The writer process can immediately recognize and acknowledge a successful commit (WriterはCommit成功を即座に認識できる).
* **Eventually Consistent Readers** :: Other concurrent reader processes observe the committed object eventually (他ReaderはEventually観測可能となる).
* **No Read-after-Write Guarantee** :: The Object Store does not guarantee immediate Read-after-Write consistency across different nodes (Object StoreはRead-after-Writeを保証しない).
--

* **Durable Object** ::
Once committed and verified, objects are read-only and durable. They cannot be overwritten or altered.

== Internal Layout and Decoupling

An Object Store implementation may incorporate internal caching or layered storage mechanisms:

* **Local Cache** ::
An ephemeral, high-speed storage layer residing close to the client process (such as a local directory cache) to accelerate file reads and staging.

* **Durable Backend** ::
A robust, distributed storage system (such as Google Cloud Storage or Amazon S3) that acts as the final destination of committed objects.

The `Repository` is **entirely unaware** (Repository はそれらを意識しません) of these internal layers. It interacts solely with the abstract Object Store interface.

== Object Commit Coordination and Leases

During concurrent file updates, multiple clients may attempt to upload and commit the same file content simultaneously. To prevent duplicate transfer and processing work, the repository uses a Lease mechanism:

=== Lease

Leases are strictly an optimization for Object Commits (LeaseはObject Commitの最適化です). They are governed by the following rules:

* **No Consistency Guarantees** ::
Leases do not guarantee metadata or transactional consistency (Leaseは整合性を保証しない).

* **Throttling and Suppression** ::
The sole purpose of a lease is to suppress and throttle duplicate, redundant Object Commit and upload tasks across concurrent writer processes (Leaseは重複Object Commitを抑制する目的である).

* **Hash-Based Boundary** ::
Leases are managed per individual content cryptographic `Hash` unit.

* **Absolute Expiration Time** ::
A Lease has an `ExpiresAt` property representing an absolute UTC timestamp after which the lease becomes invalid. It is **not** a relative Time-To-Live (TTL) duration.

* **Acquisition Check** ::
To successfully acquire a Lease, the client must verify:
+
[source,text]
----
ExpiresAt > now
----
+
If another valid active lease exists on the hash, the acquire attempt is rejected, throttling redundant upload tasks.

* **Commit Failure Expiration** ::
If a commit fails or is aborted, the lease is allowed to simply expire naturally (Commit失敗時はLeaseがExpireしてもよい).

* **Expiration is Normal Termination** ::
Explicitly releasing the lease is not the only valid termination path; lease expiration (Expire) is also treated as a normal, valid success and termination path (Releaseは正常終了時のみではなく、Expireも正常終了経路とする).
