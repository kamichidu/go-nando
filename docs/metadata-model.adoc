= Metadata Model

The Metadata Store manages the logical namespaces, attributes, and transactional states of the entries inside the repository.

== Primary Responsibilities

The Metadata Store's primary responsibilities include:

* Enforcing the unique logical namespace constraints.
* Persisting attributes (size, mtime, permissions, hash, kind).
* Executing atomic updates to entries during logical path mutations.
* Maintaining directory tree relationships.

== Entry Identifiers and Hierarchy

=== EntryID

* **Opaque Immutable Identifier** ::
Each entry is assigned a globally unique `EntryID` at the time of creation. The Repository contract guarantees only that the `EntryID` is completely immutable, opaque, and globally unique.

* **Internal Only** ::
The `EntryID` is strictly used for internal implementation logic (such as parent-child foreign key mappings) and is never exposed to users or external client APIs.
+
_Current Implementation_::
The active local scaffolding uses standard UUIDv4 for `EntryID` values.

=== Parent Relationship

Entries establish hierarchical relationships using parent pointers:

* **ParentID** ::
An entry references its parent directory via `ParentID`, which matches the parent's `EntryID`.

* **The Unique Constraint** ::
To prevent path collisions within a directory, the metadata store enforces a composite `UNIQUE` constraint on:
+
[source,text]
----
(parent_id, name)
----
+
This guarantees that no two entries with the same base name can exist under the same parent directory.

* **Path is Decoupled** ::
A fully qualified logical path (such as `/docs/report.pdf`) is not stored as the primary, unique key in the store. The primary identifier is the `EntryID`, and hierarchy is reconstructed entirely via parent-child relations.

== Metadata States

* **Ready State Only** ::
The Metadata Store only holds and represents active, visible `Ready` entries. There is **no 'Pending' state** inside the Metadata Store logical schema. The concept of a `Pending` state is strictly internal to the Object Store during upload and staging operations.

== Metadata Revision

Transactional changes are tracked using explicit version counters:

* **Type** ::
The `Revision` is defined as a `uint64` integer.

* **Monotonically Increasing Only** ::
The Repository contract guarantees only that an entry's revision is monotonically increasing (単調増加する) on each successful write transaction affecting that specific entry. It does not guarantee or assume any specific step size (such as incrementing exactly by one).

* **Per-Entry Boundary** ::
Revisions are isolated to individual entries.

* **No Parent Revision Cascade** ::
Modifying, renaming, or deleting a child entry increases the child's `Revision`, but does **not** update or cascade to the parent directory's `Revision`.

== Canonical Path

To quickly look up files by logical path, a `Canonical Path` can be computed:

* **Not the Source of Truth** ::
The Canonical Path is **never the source of truth** (正本) of the repository. It is a calculated, derived representation.

* **Path Cache** ::
The Metadata Store can materialize and maintain a path-to-EntryID mapping as a **Path Cache** (such as an index table or cache layer) to speed up logical path searches.

* **Repository Independence** ::
The Repository layer operates entirely on the basis of parent-child relationships and EntryIDs. The Repository **does not assume the existence of a Canonical Path** (Repository は Canonical Path の存在を前提としません).
