= State Machines

This document describes the state transitions and operational lifecycles for logical Entries, physical Objects, and Lease coordination keys.

== Entry Operations and Lifecycles

An Entry inside the Metadata Store represents an active, visible directory or file. Rather than transition through sequential pending states, a metadata entry is created directly as `Ready`, and then undergoes various transactional operations.

The operational branches affecting a `Ready` entry are structured as follows:

[source,text]
----
Ready
├── Update
├── Rename
├── Move
└── Delete
----

=== Operations and Revision Behavior

* **Create / Ready** ::
The entry is initialized and registered directly in the Metadata Store.
* *Revision*: Initialized to a starting `uint64` value.

* **Update** (file only) ::
The file's content reference (`Hash`) is changed to point to a newly committed Object.
* *Revision*: Monotonically increases (単調増加する) upon successful commit of the metadata update. No specific step size is assumed.

* **Rename** ::
The entry's base `Name` attribute is changed within its current parent directory.
* *Revision*: Monotonically increases (単調増加する) upon successful commit of the rename transaction.

* **Move** ::
The entry's parent relationship (`ParentID`) is changed to move the entry to a different directory.
* *Revision*: Monotonically increases (単調増加する) upon successful commit of the move transaction.

* **Delete** ::
The entry is removed from the logical namespace (such as soft deletion, marking it deleted, or absolute deletion depending on backend specifics).
* *Revision*: Monotonically increases (単調増加する) upon successful commit of the deletion transaction.

=== Revision Invariant Rules

* The `Revision` of an entry monotonically increases only upon the successful commit of any transaction altering that specific entry.
* Child operations (such as creating, renaming, moving, or deleting child entries under a directory) do **not** affect or increase the parent directory entry's `Revision`.

== Object State Machine

A physical object's lifecycle in the content-addressable storage is represented by the following sequence:

[source,text]
----
Acquire Lease -> Upload -> Commit -> Release Lease
----

=== States

1. **Acquire Lease** ::
A lease on the target cryptographic hash is acquired to coordinate the upload task.

2. **Upload** ::
The raw data bytes of the object are staged and transmitted to the Object Store.

3. **Commit** ::
The object is atomically finalized and made available in the durable CAS namespace.

4. **Release Lease** ::
The coordination lease is removed, completing the upload transaction lifecycle.

== Lease State Machine

Leases are temporal keys used to prevent redundant, concurrent uploading tasks. A Lease's state transitions are:

[source,text]
----
Acquire -> Active -> Released
           or
Acquire -> Active -> Expired
----

=== Transitions

* **Acquire** ::
A client requests a Lease on a specific cryptographic hash. If no active, unexpired lease exists on that hash, the lease is granted.

* **Active** ::
The lease is actively held, protecting the upload process. The expiration time is set: `ExpiresAt = now + TTL`.

* **Released** ::
Upon a successful Object Commit, the client explicitly deletes/releases the Lease, freeing it immediately.

* **Expired** ::
If the upload process is interrupted or fails to commit within the lease window, the lease expires silently once `now >= ExpiresAt`. Other clients can now acquire a new lease on the hash.
